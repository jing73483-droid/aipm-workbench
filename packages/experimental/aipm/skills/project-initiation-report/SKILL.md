# 产品立项报告

## 核心目标

帮助用户回答三件事：

1. 这个问题是否真实、重要且值得现在解决？
2. 为什么由我们做，第一阶段只做什么？
3. 应该立项、条件立项、转向验证，还是停止？

立项不是替一个既定方案寻找理由，而是用可追溯证据换取资源，并提前定义取舍、闸门和止损条件。

## 边界

- 上游：需求分析、用户研究、BRD 或其他问题定义材料。
- 本 Skill：判断值不值得投入、先投入什么、如何验证和止损。
- 下游：立项通过后再写 PRD、技术方案和详细项目计划。
- 若上游资料不足，可补齐立项所需的最小问题定义，但不要冒充完整 BRD。
- 不把功能清单、路线图或领导意见直接当成立项结论。
- **唯一交付物是立项报告。** 不生成 BRD、需求分析报告、用户研究报告、竞品报告、MVP 文档、评测方案、PRD 或项目计划。
- 问题定义、用户证据、竞品分析、MVP、评测和计划仅作为立项报告的内部章节与决策依据，不拆成其他报告。

## 开始前

1. 阅读用户已提供的文档、链接、数据和案例，先提取已知信息。
2. 判断项目类型：
   - `0→1`：重点检查问题真实性、市场空白、差异化与最小验证。
   - `存量产品`：重点检查漏斗/行为证据、现有能力缺口、增量价值与版本约束。
3. 判断是否为 AI 项目；若是，启用“AI 专项审查”。
4. 复述：
   - 已确认事实；
   - 当前推断；
   - 关键未知；
   - 本轮要解决的决策问题。
5. 每轮只问 3–5 个会改变结论、范围或投入的问题。不要重复询问材料中已有答案。

如需详细判断标准，读取 [methodology.md](methodology.md)。

## 证据纪律

对关键陈述使用以下标签，并在报告中保留可追溯性：

- `事实`：有可核验数据、原话、行为记录或正式文件。
- `测算`：基于明确口径和假设计算，尚非上线结果。
- `推断`：由事实推导出的判断，写清推导链。
- `假设`：尚待验证、可能被证伪的判断。
- `未知`：当前缺失且会影响决策的信息。

硬规则：

- 不虚构用户原话、样本量、市场规模、成本、收益、准确率或来源。
- 不把相关性写成因果，不把测算写成实际收益。
- 外部研究逐条附标题、来源、链接和访问日期；优先一手来源。
- 内部数据无法公开核实时，标明提供方、时间范围和口径。
- 证据冲突时并列展示，不替用户静默选择有利版本。
- 缺少关键证据时，不得给“无条件立项”。

## 四阶段显式闸门

每阶段结束时输出：

1. 当前结论；
2. 证据与反证；
3. 仍未解决的问题；
4. `建议通过 / 建议补证 / 建议停止`；
5. 请用户明确确认是否进入下一阶段。

未得到明确确认，不自动过闸。

### 闸门一：问题与对象

需要澄清：

- 谁在什么场景下遇到什么问题？
- 现有替代方式是什么，代价是什么？
- 用户说了什么、实际做了什么？
- 原始需求是问题还是预设方案？
- 为什么现在处理？

通过标准：

- 一句话问题定义中不含预设功能；
- 用户、场景、任务、阻碍、现有替代和代价可描述；
- 至少有一条真实行为证据，或明确的补证计划；
- 能说明不解决的后果。

### 闸门二：证据与机会

需要澄清：

- 问题覆盖面、频率、强度和关键分群；
- 直接竞品、间接竞品、替代方案、潜在竞品；
- 我们的优势、约束和进入窗口；
- 哪些证据支持，哪些证据反对；
- 差异化能否写成“为谁解决什么，为什么我们更适合”。

通过标准：

- 用户价值与业务价值都有证据，不只有观点；
- 竞品分析服务于具体决策，不是功能罗列；
- 有明确机会判断和最强反方论证；
- 重大未知已进入验证计划。

### 闸门三：MVP 与取舍

先写要验证的核心假设，再讨论功能。

需要澄清：

- 第一阶段只验证哪个核心假设？
- 哪些能力是验证该假设不可缺少的？
- 明确不做什么，为什么？
- POC、原型、MVP 各自是否必要？
- 成功、失败和转向的门槛是什么？

通过标准：

- MVP 是可完整使用或可完整验证的最小闭环，不是残缺功能集合；
- 每个范围项能连回问题、假设或风险；
- “必须做 / 明确不做 / 后续再做”边界清晰；
- 指标包含基线、目标、时间窗、数据源和责任人；暂无基线时写建立方式。

### 闸门四：投入与决策

需要澄清：

- 用户价值、业务/战略价值、交付可行性分别如何？
- 团队、时间、现金、数据、合规和跨团队依赖是什么？
- 关键路径、阶段闸门和资源瓶颈是什么？
- 最大风险、降级方案和停止条件是什么？
- 谁拥有最终决策，谁承担结果？

决策矩阵权重必须结合本项目目标与约束向用户确认；默认维度仅作起点，不得机械套分。

## AI 专项审查

AI 项目必须额外回答：

1. **AI 必要性**：任务是否重复、可评价且存在人力/能力瓶颈？改流程或规则能否更便宜？
2. **能力门槛**：AI 做什么；做到多好才有价值；与人工或现状相比如何？
3. **数据**：训练、知识、评测和线上反馈数据从哪里来，是否合法、可持续、可追溯？
4. **评测**：离线集、线上指标、边界样本、红线样本、分群表现和回归机制是什么？
5. **成本与延迟**：单次、单用户和规模化成本；时延、并发、供应商与降级策略。
6. **安全合规**：隐私、版权、偏见、越权、提示注入、幻觉及其他场景风险。
7. **人工兜底**：低置信度、规则冲突、申诉和高风险决定交给谁？
8. **责任边界**：AI、规则和人分别决定什么；AI 不得拥有未经授权的高风险最终决定权。

优先采用分阶段建设：

`规则与数据基线 → 离线 POC → 影子模式/小流量试点 → 有限放量 → 正式扩展`

每阶段都设置进入条件、通过门槛、失败动作和资源上限。

## 证据不足时

不要把空白补成确定答案。根据缺口给出：

- `条件立项`：方向基本成立，但存在必须先满足的依赖或门槛。
- `转向验证`：核心假设未证实，先执行最小验证计划，不进入完整开发。
- `停止`：问题/价值/能力匹配不成立，或风险不可接受。

最小验证计划必须包含：待验证假设、方法、样本/数据、通过门槛、时间、Owner、预算上限和失败后的动作。

## 最终决策类型

- **立项**：关键假设已有充分证据，范围、资源、风险和责任边界可执行。
- **条件立项**：方向成立，但必须先通过列明的前置条件或阶段闸门。
- **转向验证**：暂不批准完整项目，仅批准低成本验证。
- **停止**：不继续投入，并记录原因、已获得认知和未来重启条件。

必须先给结论，再给证据。不要用加权总分掩盖致命风险；任何红线可单独否决。

## 最终报告

仅在四阶段完成或用户明确要求形成阶段性决策时生成。

默认目录：`reports/<项目名>/`

1. 先按 [report-template.md](report-template.md) 生成 `立项报告.md`。
2. 请用户审阅并明确确认 Markdown 内容。
3. 只有确认后，才按 [html-template.md](html-template.md) 生成 `立项报告.html`。
4. Markdown 和 HTML 是同一份立项报告的两种呈现格式，不是两份不同报告。
5. 不创建任何中间报告或配套报告；所有必要内容汇入立项报告正文或附录。
6. HTML 是管理层决策页面，不是把 Markdown 机械套皮。

## 输出风格

- 一页结论优先：做不做、为什么、先做什么、投入什么、何时停。
- 正文服务管理层决策，附录服务产品与执行团队复核。
- 先问题和证据，后方案和功能。
- 图表必须回答决策问题；无真实数据时不用装饰性图表。
- 明确展示“必须做、明确不做、以后再做”。
- 主动暴露数据缺口、资源冲突、分歧和待决策项。
- 不复制任何示例项目的业务内容、数字、品牌或结论。

## 完成前质检

读取并逐项执行 [quality-checklist.md](quality-checklist.md)。存在以下任一情况，不得宣称报告完成：

- 结论与证据不匹配；
- 关键数字无来源或口径；
- 没有明确不做项；
- 指标无法采集或没有责任人；
- 计划未体现资源瓶颈和依赖；
- AI 项目缺少评测、成本、安全或人工兜底；
- 没有阶段闸门与停止条件；
- HTML 与已确认 Markdown 的结论不一致。
